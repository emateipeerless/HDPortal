3) RAW TELEMETRY TO PULL (per Device ID)
--------------------------------------------------------------------------------
A) System Info
  DeviceID, PumpType, site name, city, state, fuelTankLevel
  (see section 2)

B) Registers (run hours / related registers)
  "Pump Total Run Time"                  lifetime run hours
  Pump room temperature                  current / latest °F
                                         (temperature sensor — NOT humidity)
  Any AC power quality registers if available
                                         (voltage per leg, frequency, etc.)
  Battery voltage (if available)         for predictive trends

C) Events — pump run start/stop
  Run intervals for configurable windows:
    current calendar month
    previous calendar month
    trailing 6 calendar months (or 180 days)
    last 24 hours (for short-window jockey flags)
  Per run:
    startTime
    endTime (or unclosed)
    durationMinutes
    pump / device identity (main fire vs jockey)

  Derived per device / period:
    runCount / startsThisMonth
    periodRunMinutes / periodRunHours
    unclosedRun

D) Events — controller / impairment alarms
  Alarm intervals for period + currently active (unclosed) alarms
  Per alarm:
    alarmName
    startTime
    endTime (or still active)
    durationHours (computed)
    pump type context (Diesel vs Electric)

  Derived:
    impairedMinutes / impairedHours
    activeUnclosedImpairedAlarms[] { alarmName, startTime, durationHours }
    impairedEventCount / merged blocks (same approach as report portal)

4) STATUS CLASSIFICATION — RED / YELLOW / GREEN
--------------------------------------------------------------------------------
Each store gets exactly one current portfolio status used by:
  Dashboard red / yellow / green counts
  Sidebar / search status dots
  Site detail status badge

GREEN (No Action Required)
  Store is not currently RED or YELLOW

RED — Immediate Attention Required
  Trigger if ANY of the following is true for the store:

  R1) Impairment active > 10 hours
      Alarm name is in the diesel OR electric impairment lists below
      AND durationHours > 10 (still open / unclosed preferred)

  R2) Pump room temperature below 50°F
      Latest (or sustained) pump room temp < 50

  R3) Excessive main fire pump run events
      Main / fire pump starts in current month in excessive band
      (see section 6 — default excessive range 6–9 vs normal 3–5)
      OR equivalent short-window rule if defined later

YELLOW — Monitor Closely
  Trigger if not RED, and ANY of:

  Y1) Excessive jockey pump run events
      Jockey starts exceed jockey threshold (see section 6)

  Y2) AC power quality low
      Voltage / frequency out of acceptable band
      (exact register thresholds TBD from power quality telemetry)

  Y3) Recurring controller alarms of lower severity
      Alarm from diesel/electric impairment lists
      BUT durationHours <= 10 (not yet RED)
      AND/OR recurring pattern (count of occurrences in window TBD)

SITE ALERT ROW VARIABLES (red + yellow drill-down tables)
  storeId
  locationDisplay
  severity                 red | yellow
  reason                   one of R1–R3 or Y1–Y3 reason strings
  currentCondition         human-readable live state
                           e.g. "Engine Failed to Start — active 14 hours"
                           e.g. "Pump room temp 46°F"
                           e.g. "9 run events this month (normal: 3–5)"
  flaggedSince             datetime when the condition first became true
                           (alarm start, temp breach start, or month threshold crossed)

DASHBOARD COUNTS
  RED_COUNT                count of stores with severity = red
  YELLOW_COUNT             count of stores with severity = yellow
  GREEN_COUNT              TOTAL_STORES - unique(red∪yellow storeIds)
  TOTAL_STORES             portfolio master list length

6) PUMP ACTIVITY — JOCKEY + MAIN FIRE PUMP
--------------------------------------------------------------------------------
Windows needed per pump type (jockey vs main fire):
  startsThisMonth          count of starts in current calendar month
  startsLastMonth          count of starts in previous calendar month
  startsSixMonthBaseline   average or total starts over trailing 6 months
                           (define: mean monthly starts vs total — pick one)

Derived display fields (per flagged site):
  percentChangeFromLastMonth
      = 100 * (startsThisMonth - startsLastMonth) / startsLastMonth
      (handle startsLastMonth = 0)
  monthOverMonth
      = startsThisMonth / startsLastMonth   (display as e.g. 1.38x)
  monthOverSixMonths
      = startsThisMonth / sixMonthBaselineMonthlyAvg

JOCKEY PUMP — which sites appear on the list
  Only trouble / excessive jockey sites (not every store)
  Threshold TBD; mock UI used examples such as elevated 24h runs
  and high monthly starts vs prior month.
  Recommend defining:
    JOCKEY_EXCESSIVE_MONTHLY_STARTS     TBD
    JOCKEY_EXCESSIVE_24H_STARTS         TBD
    JOCKEY_MOM_INCREASE_PCT_FLAG        TBD (e.g. +20%)

FIRE / MAIN PUMP — which sites appear on the list
  Only trouble / excessive main pump sites
  Normal month:                         ~3–5 starts
  Excessive flagged range (current UI): ~6–9 starts this month
  Recommend constants:
    FIRE_NORMAL_MIN_STARTS              3
    FIRE_NORMAL_MAX_STARTS              5
    FIRE_EXCESSIVE_MIN_STARTS           6
    FIRE_EXCESSIVE_MAX_STARTS           9
    (sites with startsThisMonth >= 6 appear on Fire Pump Activity list;
     also feed RED reason R3 when policy says so)

JOCKEY / FIRE DETAIL TABLE COLUMNS
  storeId
  locationDisplay / city
  startsThisMonth
  percentChangeFromLastMonth
  monthOverMonth
  monthOverSixMonths

DASHBOARD COUNTS
  JOCKEY_ACTIVITY_COUNT    sites meeting jockey excessive criteria
  FIRE_ACTIVITY_COUNT      sites meeting fire excessive criteria

7) PREDICTIVE STATISTICS
--------------------------------------------------------------------------------
Sites that meet a predictive / trending rule (not necessarily red/yellow yet).

DETAIL TABLE COLUMNS
  storeId
  city / locationDisplay
  statistic                observed trend narrative or metric
  prediction               what the statistic predicts / recommended action

Example statistic types the UI expects (replace mock with computed rules):
  Jockey cycle frequency % change over N days
  Fire pump start duration trending up
  Pump room temperature trending low (e.g. toward < 55°F)
  Battery voltage decline over 14 days

Recommend defining structured fields instead of free text only:
  predictiveMetricKey      e.g. jockey_cycle_pct | start_duration_trend |
                           pump_room_temp_trend | battery_voltage_trend
  predictiveMetricValue    numeric value
  predictiveWindowDays     e.g. 14 / 30
  predictionHorizonDays    e.g. 14 / 30 / 45 / 60
  predictionText           human label for UI

DASHBOARD COUNT
  PREDICTIVE_COUNT         sites with at least one active predictive indicator

NOTE: Use pump room TEMPERATURE sensor data — not humidity.

8) AVERAGE RESOLUTION TIME
--------------------------------------------------------------------------------
Measures how long issues (red/yellow flags / impairments) take to clear.

RAW EVENTS NEEDED
  For each closed (resolved) flag or impairment in a lookback window:
    openedAt
    closedAt
    durationHours = closedAt - openedAt
    severity / category (optional weighting)

PORTFOLIO AGGREGATES
  currentHours             average resolution hours for current period
                           (e.g. current calendar month or trailing 30 days)
  currentDisplay           human string e.g. "2 days 14 hours"
  previousMonthHours       same average for previous month
  previousMonthChangePercent
      = 100 * (currentHours - previousMonthHours) / previousMonthHours
      UI treats NEGATIVE % as improvement (green)
      POSITIVE % as worse (red)
  sparklinePoints[]        monthly average hours for last N months (e.g. 7)
  sparklineLabels[]        month labels (optional; for full chart later)

DASHBOARD CARD SHOWS
  currentDisplay
  sparkline (from sparklinePoints)
  previousMonthChangePercent with green/red polarity

15) MINIMUM DATA CONTRACT TO MAKE THE DASHBOARD REAL
--------------------------------------------------------------------------------
For each Home Depot store in the portfolio:

IDENTITY
  storeId, city, state, deviceIds[], pump types at site

LIVE / PERIOD TELEMETRY (per device, then rolled up to store)
  open impairments: alarmName, startTime, durationHours
  pump room temperature (°F)
  jockey starts (month, last month, 6-mo baseline, optional 24h)
  main fire pump starts (month, last month, 6-mo baseline)
  AC power quality metrics (if available)
  battery / other predictive registers (if available)
  connectivity / online state

HISTORY (persisted)
  red/yellow status transitions
  resolved flags / impairments with open/close times
  monthly resolution-time averages

Then compute and display:
  red / yellow / green classification + counts
  impairment / predictive / jockey / fire drill-down tables
  average resolution time + sparkline + MoM %
  portfolio grade
  site detail pages from the same store-level assembly

16) QUICK MAPPING: WHERE EACH VALUE COMES FROM
--------------------------------------------------------------------------------
Store master / mapping table     → storeId, city, state, deviceIds
Device system info               → pump type, site labels, city/state check
Device events (alarms)           → impairments, durations, red R1 / yellow Y3
Device events (runs)           → jockey + fire starts, MoM, Mo6M, excessive
Telemetry registers / sensors  → pump room temp (R2 + predictive),
                                   power quality (Y2), battery trends
Persisted history DB             → status history, resolved flags,
                                   resolution-time series
Ops / CMMS (optional)            → lastInspection, work orders
Dashboard rules engine           → red/yellow/green, KPI counts,
                                   portfolio grade, site assembly
Fleet Portal UI                  → cards, tables, sidebar, search, site page
